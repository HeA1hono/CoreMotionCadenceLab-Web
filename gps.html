开始采集后，这里说明原始路程和确认距离差在哪里。静止漂移和跳点留在原始距离里，确认距离只计入跨过定位精度门的净位移。

GPS 与运动传感器来自两套独立硬件，时间戳分属不同时钟域： 后者用页面单调时钟（performance.now()），前者用墙上时间（epoch）。 本页在会话开始时取一对锚点把两者对齐，并把对齐后的残差 （latency，即"位置确定 → 我们收到"隔了多久）如实报出来， 不做自动校正——因为"真实延迟应该是多少"没有先验， 拿它去校时钟等于用被测量去校准量具。

当前是 GPX 离线回放，不是真实定位。 回放的延迟恒为 0（点是按时间线播出来的，不是测出来的）， 因此不可用这份数据评价定位性能或 GPS 精度。 另请留意下方"文件来历"：本仓库可用的 GPX 多由跑道几何参数生成。

不把 GPS 配速换算成步数。步数 = 距离 ÷ 步幅 需要先假设步幅，假设一错步数就是编的。GPS 只用来质疑步频， 不用来产生步频。

⑤ 导出

三个文件各自的来源标记不同：轨迹与时间轴带 REAL_GPS / REPLAY，诊断 JSON 额外记录 provenance（GPX 文件自身是实测还是几何生成）。 文件名里也带来源，便于在文件管理器里分辨。

阶段说明

  • 本页不计算准确率。它只把两个源的采样、时间戳与中断摊在同一根轴上， 让人能看出"哪个源在什么时候没给数据"。准确率必须由真机人工对照实验给出。
  • 步频仍是 E-W3.1 那套算法，参数版本见页脚。本阶段没有修改 已验证的步频核心逻辑，只增加了对它的独立观测手段。
  • 不向系统定位服务写入任何东西。只读 watchPosition， 不读写 CMPedometer，不接触任何第三方运动 App。
  • GPX 回放不是测量。回放数据的"延迟恒为 0"是构造出来的， 把它当定位性能会得出完全错误的结论。
  • 页面必须顶层打开。iOS 26 存在 iframe 内 devicemotion 不派发的已知缺陷（WebKit Bug 301294）。
